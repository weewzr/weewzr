## The problem

The README names the user of KASCO as a Sustainable Aviation Fuel (SAF) network planner who must decide where to commit about USD 4.7B of plant capital before engineering starts. It describes the usual alternative as comparing a few hand-drawn layouts in a spreadsheet. KASCO is a working prototype, built for Airbus Challenge 3, Autonomous SG 2026. It picks refinery and depot sites and sizes across Kalimantan and routes biomass and SAF to four international airports. It also shows the evidence behind each number. The planner makes the decision, and the tool does not claim to replace engineering judgement.

The inputs are the official challenge data. Demand is 300 kt of SAF at each airport, 1,200 kt in total, which needs 6,000 kt of biomass at a yield of 0.20 t SAF per t biomass. CapEx is straight-line over 20 years and fixed OpEx is 5% of CapEx. Distance is great-circle times 1.3, and the last leg to Tarakan is by barge.

## Objectives

The README lists five deliverables, and the live app is the demonstration of all of them.

| Deliverable | Where it is |
|---|---|
| Interactive map | Network map tab: 80 sites, flows by leg, layer toggles, side-by-side comparison |
| Optimisation engine | `crates/engine`: Lagrangian branch-and-bound, exact min-cost flow, continuous location refinement |
| Scenario simulator | Optimisation and Scenario analysis tabs: every input is editable and reruns the real solver in the browser |
| Decision support | Decision support tab: rule-based and traceable, plus the optional Ask Claude Sonnet 5.5 panel |
| Evaluation and evidence | Evaluation and Reports tabs, and `docs/reports` |

The design goal behind them is that each number comes with its status. A result is labelled as proven within a gap, as a local refinement with no global proof, or as a heuristic, and the app shows which label applies.

## Architecture

The engine is a Rust workspace with three crates. The browser build and the command-line runner share the engine code, so the numbers on the page come from the same functions that the tests and the HiGHS cross-checks exercise.

| Component | Path | Role |
|---|---|---|
| Engine | `crates/engine/src/` | `data.rs` (official datasets compiled into the binary), `params.rs` (every input, official values as defaults), `problem.rs`, `solver.rs`, `flow.rs`, `location.rs`, `field.rs`, `baseline.rs`, `solution.rs`, `validate.rs`, `diag.rs`, `explain.rs`, `scenarios.rs` |
| Command line | `crates/cli/` | Solves every scenario and writes the JSON the web app reads (`saf all [seconds]`), and exports the candidate-site model as an LP file (`saf lp`) |
| Browser entry | `crates/wasm/` | Exports `alloc`, `dealloc` and `call`. JSON goes in and out through linear memory, so the page needs no glue library |
| Web app | `docs/` | `index.html`, `app.js`, `worker.js`, `assistant.js`, `style.css`, `saf.wasm` and the stored results in `docs/data/` |
| Data | `data/` | Official workbook and airport file, biomass sites, OSRM road matrix, Natural Earth land mask |
| Checks | `scripts/` | Python for data fetching, HiGHS cross-checks and `check_official.py`, and `check_ui.mjs` for the front end |

The data flow runs from the official inputs through the solver to the interface. `data.rs` holds the datasets and `params.rs` the editable inputs. `problem.rs` turns a scenario into a numeric instance, `solver.rs` searches the refinery sites, and `flow.rs` prices every candidate by min-cost flow. `location.rs` then moves plants on land, and `solution.rs` builds the result records from flows and facility lists. `validate.rs` audits the finished network from those records alone, and `explain.rs` answers questions from the result fields. In the browser the app (`app.js`) sends JSON to `worker.js`, which runs `saf.wasm`. Figures shown before any run come from the committed JSON in `docs/data/`. Cancel replaces the worker, because the engine cannot be interrupted from inside it.

There is no CI workflow in the repository. GitHub Pages serves the `docs` folder of the main branch, so merging to `main` publishes the site, and the README asks for `npm run check:ui` to be run before publishing.

## Approach

The candidate-site model is a capacitated facility location problem. Relaxing supply and demand with multipliers splits it into one small subproblem per site, which gives a proven lower bound, and branch-and-bound then searches refinery sites. A min-cost flow gives the optimal routing for any set of open refineries. Plants are then free to move anywhere on land to their weighted geometric median, with a land check. That last step is a local refinement.

Under these inputs depots sit at refineries. The second leg costs more per tonne-km than the first and depots lose no mass, so the triangle inequality shows that moving a depot onto the single refinery it serves never raises transport cost. `scripts/verify_depots.py` closes the harder case of depots feeding two refineries for the base fleet. Real wet feedstock could change this, so a field-depot design is included as a priced alternative.

The solver is written in Rust and compiled to WebAssembly, so the whole product runs in the browser from GitHub Pages with no server. The scenario tabs let the user edit every input and rerun the real solver. The decision-support tab is rule-based and traceable, and it uses no language model. It declines questions outside the model. An optional panel using Claude Sonnet 5.5 answers free-form questions from solver data with the viewer's own API key, and removes any line whose figure is not in that data.

The comparison designs in `baseline.rs` are a greedy layout (depots on the richest sites, refineries farthest-first), an airport-first layout and a k-means benchmark with 50 restarts that is handed the same fleet and refinement.

## Algorithms and models

### Mixed-integer model

File: `docs/MODEL.md`; implemented in `crates/engine/src/problem.rs` and `solver.rs`.

Flows are x<sub>ij</sub> from biomass site i to depot j, u<sub>jk</sub> from depot j to refinery k and w<sub>ka</sub> from refinery k to airport a, all in kt per year. The variable y<sub>js</sub> is the integer number of depot modules of size s at j, z<sub>ks</sub> is binary and says whether a refinery of size s is open at k, and t<sub>js</sub> and r<sub>ks</sub> are the throughputs by size (kt per year). The objective is the annual cost in USD M per year:

min ( 1/n + f ) [ Σ F<sup>D</sup><sub>s</sub> y<sub>js</sub> + Σ F<sup>R</sup><sub>s</sub> z<sub>ks</sub> ] + Σ v<sup>D</sup><sub>s</sub> t<sub>js</sub> + Σ v<sup>R</sup><sub>s</sub> r<sub>ks</sub> + Σ τ<sub>1</sub> d<sub>ij</sub> x<sub>ij</sub> + Σ τ<sub>2</sub> d<sub>jk</sub> u<sub>jk</sub> + Σ τ<sub>3</sub> d<sub>ka</sub> w<sub>ka</sub>

where F is CapEx (USD M), n = 20 years is the CapEx life, f = 0.05 per year is the fixed OpEx share, v is variable OpEx (USD per t), τ is the tariff (0.10, 0.12 and 0.08 USD per t per km) and d is distance (km, great-circle times 1.3). The constraints, in the same units, are:

Σ<sub>j</sub> x<sub>ij</sub> ≤ B<sub>i</sub>, Σ<sub>i</sub> x<sub>ij</sub> = Σ<sub>s</sub> t<sub>js</sub>, t<sub>js</sub> ≤ C<sup>D</sup><sub>s</sub> y<sub>js</sub>

Σ<sub>k</sub> u<sub>jk</sub> = ρ Σ<sub>i</sub> x<sub>ij</sub>, Σ<sub>j</sub> u<sub>jk</sub> = Σ<sub>s</sub> r<sub>ks</sub>, r<sub>ks</sub> ≤ C<sup>R</sup><sub>s</sub> z<sub>ks</sub>

Σ<sub>a</sub> w<sub>ka</sub> = η Σ<sub>s</sub> r<sub>ks</sub>, Σ<sub>k</sub> w<sub>ka</sub> ≥ D<sub>a</sub>, Σ<sub>s</sub> z<sub>ks</sub> ≤ 1

where B<sub>i</sub> is the biomass available (kt per year), D<sub>a</sub> the SAF demand (300 kt per year at each airport), C the biomass intake capacity (kt per year), η = 0.20 t per t the yield and ρ = 1 the depot mass retention. The official CapEx values are USD 2.25M and 4.5M for small and large depots and USD 480M and 765M for small and large refineries, and the official capacities are 150 and 300 kt per year for depots and 500 and 1,087 kt per year for refineries. `scripts/check_official.py` compares these inputs with the official workbook.

### Lagrangian bound and branch-and-bound

File: `crates/engine/src/solver.rs`.

The supply and airport demand constraints are relaxed with multipliers, one per biomass site and one per airport. The relaxed model splits into one small subproblem per site, each solved greedily and exactly, and the sum is a valid lower bound on the cost. The relaxed problem may choose one site in both sizes, which keeps the bound valid. Subgradient steps tighten the multipliers, and branch-and-bound forces or bans refinery sites. Biomass sites are near-substitutes, so most of the bound comes from the root relaxation. The gap is the difference between the best feasible cost and the bound, taken relative to the feasible cost.

### Exact flows

File: `crates/engine/src/flow.rs`.

For a fixed set of open facilities, the allocation is a min-cost flow, solved by successive shortest paths with node potentials. The graphs have about a hundred nodes, so a dense Dijkstra is used.

### Continuous refinement

File: `crates/engine/src/location.rs`.

With flows fixed, each refinery moves to the weighted geometric median of the points it exchanges material with, found by Weiszfeld iteration. With locations fixed, min-cost flow re-routes all material. The two steps alternate, which is Cooper's location-allocation method. It converges to a local optimum with no global proof, and plants stay on land.

### Why depots sit at refineries

File: `docs/MODEL.md`.

For biomass moving from site i through depot j to refinery k, the transport cost per tonne is τ<sub>1</sub> d<sub>ij</sub> + ρ τ<sub>2</sub> d<sub>jk</sub>. If ρ τ<sub>2</sub> ≥ τ<sub>1</sub>, this is at least τ<sub>1</sub> ( d<sub>ij</sub> + d<sub>jk</sub> ) ≥ τ<sub>1</sub> d<sub>ik</sub> by the triangle inequality, so a depot that serves one refinery costs no more when placed at that refinery. The statement holds for metric distances, ρ τ<sub>2</sub> ≥ τ<sub>1</sub> and this fleet, and it reverses below ρ = 0.833, which is τ<sub>1</sub> / τ<sub>2</sub> for the official tariffs. A depot that feeds two refineries needs a separate argument, which `scripts/verify_depots.py` supplies with HiGHS for the base fleet.

## Verification

`validate.rs` recomputes every balance and the objective from the flow records. It reads only flow records, facility records and official inputs and shares no code with the solver, so a modelling slip cannot pass in both places. HiGHS provides a second opinion from an exported LP file.

| Result | Status |
|---|---|
| Base case, 70 candidate sites | Feasible within a proven gap |
| Five smaller cases | Rust cost equals the HiGHS proven optimum |
| Refined coordinates | Local refinement, no global proof |
| Field depots | Heuristic, no optimality proof |

On the five smaller cases (total demand from 20 kt to 300 kt), HiGHS proved the optimum. The Rust cost matched it and the Rust bound stayed valid. On the full base case the exported model went to HiGHS with a 480 s time limit. HiGHS returned an objective of USD 890.32M and stopped at the limit with a 2.65% remaining gap, so it gives no optimality proof on the full base case. The base-case gap rests on the Rust bound. With the six base refineries fixed and depots free to go anywhere, HiGHS proved that the co-located cost of USD 890.32M is optimal (docs/data/depot_check.json). `scripts/check_official.py` compares the engine with the official workbook, and the recorded check holds 30 comparisons, all passed.

The engine has 38 tests (`cargo test --release -p saf_engine`, as recorded in the README). The front-end checks (`npm run check:ui`) ran 64 of 64 checks, and axe-core 4.14.0 reported no violations on the seven tabs at 1440 by 900 and at 390 by 844 pixels. The README states that this was not tested with a screen reader. The HiGHS scripts were not rerun in that review, because the engine, data and WASM file were unchanged.

## What it does not cover

- The 80 biomass points are official modelling inputs and have not been surveyed as sites, and 13 fall off the coastline.
- Site screening is preliminary. Land tenure is unchecked, and so are peat and forest status, so no site is shown to be buildable.
- Official demand is about 12 times the project's estimate of today's real jet use at these airports, so this is a hub-scale plan.
- The model is deterministic and annual, and biomass purchase price is outside the objective by instruction.
- Refined coordinates carry no global proof, and the field-depot design carries no optimality proof.
- The depot result reverses if depot mass retention falls below 0.833.
- Accessibility was not tested with a screen reader, and map flow lines cannot take keyboard focus.

## Technology

The engine and a command-line runner are Rust crates, and so are the browser entry points. The browser build targets `wasm32-unknown-unknown` with a plain HTML, CSS and JavaScript front end that has no bundler, Leaflet for the maps and Chart.js for the charts. HiGHS and Python scripts perform the independent checks and generate the reports. Data comes from the official Airbus files and a Natural Earth land mask, and road distances come from OpenStreetMap through OSRM. GitHub Pages serves the `docs` folder. The code is MIT licensed. The development-only dependencies for the front-end checks are `axe-core` and `puppeteer-core`, and nothing is bundled into the served site.
